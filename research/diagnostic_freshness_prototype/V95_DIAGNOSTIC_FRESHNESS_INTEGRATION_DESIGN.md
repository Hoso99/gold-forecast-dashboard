# V9.5 Diagnostic Freshness — Integration Design

Status: RESEARCH PROPOSAL ONLY
Deployment: NOT APPROVED
Scope: V9.5 PAPER journal observability
V9.4 LIVE: OUT OF SCOPE

## 1. Objective

Distinguish diagnostic values recalculated during the current
evaluation cycle from values inherited from previous cycles.

This change must never alter trading decisions.

## 2. Proposed integration points

### cycle() — v95_paper_monitor.py:538

Generate a unique cycle identifier at the beginning of each cycle.

Initialize fresh evidence independently of persisted trading state.

Market-closed cycles must not inherit previous diagnostic freshness.

### evaluate() — v95_paper_monitor.py:201

Track component-level evaluation evidence.

Record calculation completion at these locations:

- Lines 317–322: diagnostics and research_votes
- Lines 324–327: shadow_entry
- Lines 391–392: core_sell_detectors

Successful calculations are marked RECALCULATED.

Handled calculation failures are marked UNAVAILABLE.

Components not reached are marked NOT_RECALCULATED.

Missing or unverified evidence is marked UNKNOWN.

### journal_decision() — v95_paper_monitor.py:497

Add observational metadata only:

- evaluation_cycle_id
- diagnostics_freshness
- component_freshness
- diagnostics_cycle_verified
- latest_available_m1_utc
- last_diagnostics_evaluated_m1_utc

Preserve all existing journal fields.

Do not infer diagnostic recalculation from last_bar alone.

## 3. Freshness classification

CURRENT:
All four components recalculated in the verified cycle.

PARTIAL:
Verified cycle with a mixture of recalculated,
unavailable, or skipped components.

STALE:
Verified cycle with no component recalculation.

UNKNOWN:
Missing, invalid, or mismatched cycle evidence.

## 4. Evidence integrity

Evidence must be generated by actual evaluation code.

Do not infer completion from:

- Existing diagnostic dictionaries
- Decision names
- M1 timestamps alone
- Previous-cycle state
- Caller assertions without verified instrumentation

Component evidence must be reset every cycle.

## 5. Trading invariants

No changes permitted to:

- SELL-only entry logic
- Existing-position protective monitoring
- Stop-loss or take-profit calculations
- C2 Raw exits
- Risk limits
- ATR thresholds
- Data collectors
- Market-data synchronization
- Telegram alert generation or delivery
- V9.4 LIVE

Freshness classification must never gate a trade.

## 6. Required validation before deployment

- Existing V9.5 regression suite passes.
- New freshness regression suite passes.
- Market-closed cycles cannot inherit freshness.
- WAIT_DATA preserves existing trading behavior.
- HOLD_SELL can report partial diagnostic freshness.
- Protective exits preserve existing priority.
- Telegram output and delivery remain unchanged.
- Missing evidence fails closed to UNKNOWN.
- Journal records preserve existing fields.
- No trading-decision differences in controlled replay.
